# 测试指南

自动测试验证本地分类、通知年龄分段、去重清理和 Manifest 权限；真实 X 抓取必须在 Microsoft Edge 和已登录的 X 会话中手动验证。

## 1. 自动测试

要求 Node.js 20 或更高版本：

```bash
npm test
npm run check
```

预期：所有测试通过，静态检查显示 Manifest V3、版本号、文件引用和权限范围均有效。

## 2. Edge 本地加载

1. 打开 `edge://extensions/`。
2. 开启“开发人员模式”。
3. 选择“加载解压缩的扩展”。
4. 选择包含 `manifest.json` 的项目根目录。
5. 打开扩展弹窗，确认版本为当前项目版本且无 Manifest 错误。
6. 打开“背景页 / Service Worker”检查控制台无未处理异常。

## 3. 正常监测测试

1. 在同一 Edge 配置文件中登录 X。
2. 点击“打开 X 搜索页”。
3. 确认页面搜索条件包含 `from:thsottiaux`、`since:`、`until:`，且使用“最新”结果。
4. 点击“立即检查”。
5. 观察状态从“检查中”变为“正常”或“补查不完整”。
6. 检查以下字段是否更新：最近成功、最近尝试、成功至今、补查范围、帖子数量和滚动次数。
7. 关闭弹窗后重新打开，确认状态仍然存在。
8. 确认没有为同一帖子重复发送通知。

## 4. 72 小时断档补查测试

此测试不使用模拟数据冒充真实抓取。

1. 在 `edge://extensions/` 打开扩展的 Service Worker 控制台。
2. 在控制台执行：

   ```js
   chrome.storage.local.get("runtimeState").then(({ runtimeState }) =>
     chrome.storage.local.set({
       runtimeState: {
         ...runtimeState,
         lastSuccessfulCheckAt: new Date(Date.now() - 80 * 60 * 60 * 1000).toISOString(),
         lastBackfill: null
       }
     })
   )
   ```

3. 回到弹窗点击“立即检查”。
4. 打开 X 搜索页，观察页面继续向下滚动，而不是停在顶部一条或固定 20 条。
5. 观察同一个后台标签页依次切换多个日期查询；精确 72 小时通常跨 4 个 UTC 日期区间。
6. 检查弹窗进度是否显示“日期 1/4”等分段信息，以及当前页可见帖子数和滚动次数。
7. 若每个日期页都耗尽 X 当前提供的可见结果，弹窗应显示“分段补查完成”，并分别显示“全部帖子”“额度相关”和“重置”数量。
8. 若任一日期页达到安全上限或无法读完，确认同一后台标签页会切换到 Tibo 的“帖子与回复”页回退检查；最终应显示“可能不完整”并保存原因。
9. 检查历史中 6–24 小时、24–72 小时的事件是否标记“延迟发现”。
10. 确认超过 72 小时的相关帖子不产生系统通知。

过滤显示验证：确认“全部帖子”通常大于或等于“额度相关”，而下方事件历史只包含额度相关消息。重复出现在搜索页与主页的同一帖子只能计数一次。

测试完成后再次正常检查即可刷新状态；如需完全清理测试状态，可卸载并重新加载扩展。

## 5. X 登录失效测试

1. 暂停扩展。
2. 在 X 中退出登录，或使用一个没有 X 登录状态的独立 Edge 测试配置文件。
3. 重新启用扩展并点击“立即检查”。
4. 预期弹窗显示：

   > X登录状态可能已失效，请先在Edge中登录X，然后重新检查。

5. 预期收到一次登录失效系统通知；12 小时冷却期内不应反复骚扰。
6. 登录 X 后点击“立即检查”，预期 `xLoginStatus` 恢复为已登录，检查可以继续。

## 6. 通知测试

1. 在弹窗或设置页点击“测试通知”。
2. 确认 Windows 通知中心出现统一图标和简洁中文文案。
3. 若没有通知，检查 Windows 设置 → 系统 → 通知、Edge 通知权限和勿扰模式。
4. 对真实命中的公开帖子，确认通知点击后打开正确的 `@thsottiaux/status/{id}` 原帖。
5. 检查已完成重置的通知只建议“检查新额度”，不建议消耗旧额度。
6. 检查延迟通知包含发帖时间、发现时间和相对时间。

## 7. 后台和恢复测试

1. 开启 Edge“关闭 Microsoft Edge 后继续运行后台扩展和应用”。
2. 记录最近一次成功检查时间，关闭所有 Edge 窗口，但不要从系统托盘完全退出 Edge。
3. 等待至少一个检查周期后重新打开 Edge，检查最近尝试时间是否推进。
4. 让电脑休眠超过 10 分钟，再唤醒并打开 Edge。
5. 下一次闹钟触发后应启动按日期分段的 72 小时补查。
6. 从系统托盘完全退出 Edge，确认文档所述限制：扩展不会继续实时工作。

## 8. 升级测试

1. 保留一个已安装的旧版本和若干去重 ID / 历史记录。
2. 用新文件覆盖项目目录。
3. 在 `edge://extensions/` 点击“重新加载”。
4. 确认旧的 `seenIds` 被迁移到 `processedPostIds`，已处理帖子不会重复通知。
5. 确认版本升级后自动启动 72 小时补查。

## 9. X 页面结构回归

每次发布前至少确认：

- `article[data-testid="tweet"]` 仍能定位结果；
- `[data-testid="tweetText"]` 仍能读取主帖文字；
- `time[datetime]` 或等价 `time` 元素仍提供发布时间；
- `@thsottiaux/status/{id}` 链接仍可验证发布账号和帖子 ID；
- 原创、回复和引用帖至少各抽查一个真实样例；
- 页面登录墙和常见错误提示仍能被识别。

## 10. Edge / Chrome 与语言切换测试

1. 在中文界面的 Edge 加载扩展，确认弹窗、设置页和测试通知为中文，并显示 Microsoft Edge。
2. 在英文界面的 Chrome 加载同一目录，确认弹窗、设置页和测试通知为英文，并显示 Google Chrome。
3. Chrome 测试通知正文不得再出现 Edge；Edge 的后台运行建议不得显示 Chrome 设置路径。
4. 修改浏览器界面语言并完全重启浏览器后，重新加载扩展，确认界面跟随新的浏览器语言。
5. 确认英文界面打开英文隐私说明，中文界面打开中文隐私说明。

## 11. 72 小时累计已知与诊断测试

1. 完成一次补查并记录“本次读取”和“72小时累计已知”。
2. 数分钟后再次补查；即使本次读取变少，只要旧帖子仍在72小时窗口内，累计已知不应因单次漏回而减少。
3. 若第二次发现新帖子，累计已知应按帖子 ID 去重后增加。
4. 展开“按日期检查诊断”，确认每个日期区间显示本次数量、累计数量、相关数量、滚动次数和完成状态。
5. 将测试观察记录的发布时间推进到72小时以前，确认下一次检查后从累计已知中清理。
6. 修改补充额度词语后，确认累计分类缓存会重建，避免按不同规则计算的相关数量混在一起。
